## 1. 목적

북미 서비스 데이터를 기준으로 기사 배정과 방문 순서를 계산하고, 이를 검토용 지도, 시뮬레이션 결과, 운영 API 형태로 재사용할 수 있는 라우팅 플랫폼을 구축한다.

현재 프로젝트는 다음 3개 축으로 운영된다.

1. 애틀랜타 중심의 생산/시뮬레이션 라우팅
2. Live Atlanta 운영 라우팅
3. 공통모드(Common VRP Mode) 기반 범용 클라이언트/서버 라우팅

공통모드는 특정 도시 전용 스크립트에 묶이지 않고, 도시/법인/기사/서비스 입력을 공통 구조로 정규화한 뒤 같은 API와 같은 저장 구조로 처리하는 것을 목표로 한다.

### 1.1 Canonical 데이터 파이프라인

2026-07-18부터 북미 데이터의 active root는 `data/north_america/`이며,
`config/data_catalog.json`이 원본 service, geocoded service, 원본/운영 profile,
region candidate/reviewed/seed, 개발/운영 runtime 경로를 하나로 결정한다.

```text
raw service/profile
  -> curated service/profile
  -> planning region candidates
  -> reviewed fixed regions
  -> DB seed regions
  -> client upload / VRP runtime
```

Candidate는 DB나 지도 운영 입력으로 직접 사용할 수 없다. Postal coverage 100%,
중복 0건 검증과 명시적 promotion을 통과한 reviewed plan만 지도에서 읽고 DB seed로
변환한다. 상세 경로, migration, 실행 명령은 `docs/data_pipeline.md`를 따른다.

기사 배정 정책은 도시별로 분리한다.

- Atlanta: `home_distance_only`; preferred region penalty를 사용하지 않는다.
- Los Angeles: `preferred_region_soft`; 다른 region 배정에 soft penalty를 적용한다.

두 정책 모두 capability, fixed job, slot, work/travel limit은 유지한다.

## 7. 공통 payload 생성 로직

`smart_routing/common_vrp_runtime.py`의 payload 생성 순서:

1. 서비스 행과 technician 행을 DataFrame으로 변환
2. available technician만 선별
3. 기사 마스터와 라우팅 설정 조회
4. 기사 시작점이 `Home`이면 home 좌표 사용
5. 기사 시작점이 `Custom Address`이면 지오코딩 수행
6. 기사 시작 좌표 기준으로 서쪽에서 동쪽 순 정렬
7. technician payload 생성
8. job payload 생성
9. request_id, mode, planning_date, options 포함 최종 payload 반환

기본 옵션:

- `respect_fixed_jobs = true`
- `objective = min_total_travel_time`
- `time_limit_seconds = 30`
- `timezone_offset = routing config 값`

job payload 핵심 필드:

- `salesforce_id`
- `receipt_no`
- `product_group`
- `product`
- `symptom`
- `address`
- `city_name`
- `state_name`
- `country_name`
- `postal_code`
- `location`
- `fixed`
- `current_employee_code`
- `current_center_type`

technician payload 핵심 필드:

- `employee_code`
- `employee_name`
- `center_type`
- `start_location`
- `end_location`
- `shift_start`
- `shift_end`
- `slot_count`
- `max_jobs`

Slot capacity 기준:

- `slot_count`는 해당 routing 실행에서 technician이 소화할 수 있는 slot capacity의 원천 값이다.
- Common VRP 결과 화면의 Fill Rate 분모는 배정된 technician들의 `slot_count` 합계를 기준으로 한다.
- VRP solver 내부에서는 fixed job을 반드시 유지하기 위해 특정 technician의 `max_slots`가 fixed slot 수까지 일시적으로 확장될 수 있다.
- 이 내부 확장값은 solver feasibility용이며, Fill Rate 분모에는 반영하지 않는다.
- 따라서 fixed job 때문에 실제 배정 slot이 technician list capacity를 넘으면 Fill Rate가 100%를 초과할 수 있다. 이 값은 capacity 초과 배정 신호로 해석한다.
- 결과 화면에서 technician master에 없는 code가 있을 때만 result payload의 `max_slots`를 보완 fallback으로 사용한다.

## 10. 북미 라우팅 기본 관점

북미 라우팅은 한국식 순차 시간표 배정 문제가 아니다.

- 한국: 접수 순서와 슬롯이 중요하다.
- 북미: 하루 접수 건을 먼저 모은 뒤 batch routing으로 실행 순서를 결정한다.

초기 설계 목표는 단순 이동거리 절감이 아니라, 인접 지역을 통합했을 때 필요한 유효 SM 수를 추정하고 이동거리와 배정 균형을 함께 관리하는 것이었다.

초기 region design 흐름:

1. `STRATEGIC_CITY_NAME + POSTAL_CODE` 기준 서비스 volume 집계
2. city-level 일평균 서비스 수요 산정
3. city별 필요 SM 수 계산
4. postal centroid 기반 weighted geographic clustering
5. integrated region별 서비스 수, ZIP 수, 필요 SM 수, SM당 서비스 수 산출

초기 가정:

- `1 receipt = 1 service job`
- `REPAIR_RECEIPT_TIMESTAMP` 순서는 batch optimization priority로 사용하지 않음
- 초기에는 모든 active SM이 모든 제품을 수리할 수 있다고 단순화
- 생산 라우팅은 점차 실제 service time과 travel time 기반으로 이동했다.

## 11. Region Design과 후보 region sweep

초기 integrated region 설계는 아래 방식들을 비교했다.

- `balanced`: 거리 + 서비스 균형 + radius penalty
- `weighted_kmeans`: 단순 weighted k-means 기반 접근

후보 region count sweep:

- Atlanta candidates: `2, 3, 4, 5`
- Los Angeles candidates: `3, 4, 5, 6`

비교 지표:

- average deployed SM count
- average jobs per SM
- jobs-per-SM standard deviation
- average distance per SM
- average duration per SM
- `p95` and `max` of daily total workload per SM
- `480 min` overflow count and overflow ratio
- `balance_score`

해석:

- 통합 region 수가 너무 적으면 SM 수는 줄지만 거리와 duration 증가가 커진다.
- staffing efficiency를 주장하려면 region 수뿐 아니라 geographic span과 max radius도 함께 제약해야 한다.

## 12. 지도/영역 Explorer 설계

`sr_area_map.py`는 지역 설계와 실제 서비스 분포를 비교하는 지도 UI다.

핵심 설계:

- `AREA_NAME`, `STRATEGIC_CITY_NAME`, `SVC_ENGINEER_CODE` 등 key text 필드는 trim/newline 제거 등 정규화 후 group/merge한다.
- `area_km2 = 0`은 실제 면적 0이 아니라 key normalization 또는 geometry join 문제일 수 있다.
- city-level map dataset은 `data/cache/area_map/<city_slug>/` 아래 캐시한다.
- profile workbook, ZCTA ZIP file, selected geocoded service file의 path와 modification time이 cache metadata와 같을 때만 cache reuse를 허용한다.
- Folium 렌더링 비용을 줄이기 위해 simplified geometry를 캐시한다.
- ZIP/AREA tooltip은 geocoded service file의 실제 `POSTAL_CODE` 서비스 수를 사용한다.
- AREA polygon이 색상 의미를 갖고, ZIP polygon은 얇은 중립 boundary로 표시한다.
- 같은 ZIP이 여러 `AREA_NAME`에 중복 배정된 경우 가장 빈도가 높은 primary area를 사용한다.

Integrated region map:

- 최신 `region_design_postal_*.csv`를 사용한다.
- postal assignment를 dissolve해 integrated region polygon을 만든다.
- `service_gap_pct`, `max_radius_km`, `avg_radius_km`를 노출한다.

운영 메모:

- 기존 region map은 전체 center type을 보존한다.
- integrated-region 계산은 여러 차례 DMS/DMS2-only에서 full workload 포함으로 변경되었다.
- ASC 스타일링은 current-region과 integrated-region에서 의미가 다르므로 분리한다.
- 지도 cache와 route-geometry cache는 route explorer 성능에 중요하다.

## 13. 애틀랜타 생산 라우팅 설계

애틀랜타 생산 라우팅은 초기 integrated-region 실험과 분리된 deterministic production track이다.

기준:

- City: `Atlanta, GA`
- Fixed region count: `3`

## 15. 애틀랜타 생산 배정 로직

북미 batch routing에서는 assignment order와 final visit order를 분리한다.

아래 내용은 기존 deterministic Atlanta production track의 `seed + grow` 모델이다.
공통 VRP client의 Atlanta 실행 정책과는 구분한다.

1. date별 active engineer pool 생성
2. 가능한 경우 각 engineer에 초기 nearby job seed 배정
3. 남은 job마다 candidate engineer 평가
4. repairability constraint 확인
5. DMS/DMS2 eligibility 확인
6. actual attendance limit 적용 여부 확인
7. legacy production 비교 모드에서는 soft-region penalty 적용 가능
8. current workload와 proximity 평가
9. 최종 배정 후 OSRM route construction으로 방문 순서 재생성

공통 VRP client의 `Atlanta, GA`는 `home_distance_only` 정책이므로
`preferred_region_name`을 solver 비용에 전달하지 않는다. 따라서 region 경계 대신
기사 home에서 출발하는 도로 이동시간이 지리적 배정 기준이 된다. 반대로
Los Angeles 계열 context만 `preferred_region_soft`를 사용한다.

중요한 변경:

- grow scoring은 engineer의 마지막 stop만 보지 않는다.
- 새 job은 engineer home/start point와 이미 배정된 모든 customer point 중 가장 가까운 anchor를 기준으로 scoring한다.
- 즉, route chain tail이 아니라 existing cluster 주변 업무를 흡수하는 방식이다.

Final route order:

- assignment order는 최종 방문 순서가 아니다.
- assignment 완료 후 route를 다시 만들고 final stop sequence를 별도 생성한다.
- 표시 distance, duration, schedule은 OSRM route construction을 기준으로 한다.

Rebalance:

- 이전 worst-route one-job move post-processing은 현재 비활성화되어 있다.
- straight-line 기반 post move가 실제 road route를 악화시키는 경우가 있었고, OSRM 기반 local improvement는 multi-day rebuild에서 비용이 컸기 때문이다.

### 15.1 VRP slot/work limit 정책

`smart_routing/production_assign_atlanta_vrp.py`의 OR-Tools VRP 경로는 slot capacity와 작업시간을 동시에 제약한다.

Slot 제약:

- 기본 slot hard limit은 technician payload의 `slot_count`/`max_slots`를 따른다.
- fixed job이 이미 technician slot capacity를 초과하면 fixed job 보존을 위해 해당 technician의 내부 `max_slots`를 fixed slot 수까지 확장한다.
- 이 확장은 fixed job feasibility를 위한 solver 내부 처리이며, 운영 KPI의 capacity 분모에는 사용하지 않는다.

작업시간 제약:

- 기본 soft limit은 `VRP_SOFT_WORK_MIN = 540`분이다.
- 일반 hard cap은 `VRP_ABSOLUTE_WORK_MIN = 600`분이다.
- `VRP_OVERTIME_ALLOWANCE_MIN = 60`분을 사용해 540분을 약간 넘기는 해는 허용하되, 일반적으로 600분을 넘지 않게 한다.
- fixed job 자체가 이미 600분을 넘길 수밖에 없는 경우에는 fixed job 최소 예상 작업시간에 `VRP_FIXED_WORK_BUFFER_MIN = 30`분만 추가로 허용한다.
- 결과 summary에는 `hard_work_limit_min`을 포함해 해당 technician/day에 실제 적용된 hard work limit을 확인할 수 있게 한다.
- `max_work_min_per_sm_day`는 미배정을 줄이기 위한 fallback 완화값이지만, 운영 화면에서는 `total_work_min`, `overtime_min`, `over_soft_limit`, `over_absolute_limit`을 함께 확인해야 한다.

## 16. Actual Attendance 설계

Actual Attendance variant는 full modeled pool이 아니라 실제 일별 출근 제약을 유지했을 때 새 라우팅이 실행 가능한지 보는 모드다.

규칙:

- 실제 근무한 engineer를 우선 사용한다.
- 실제 근무 engineer가 현재 roster에 없으면 current roster engineer로 대체할 수 있다.
- replacement는 real headcount gap 범위 안에서만 허용한다.
- dispatchable engineer count는 실제 daily working headcount와 맞춰야 한다.
- non-roster engineer에게 일을 배정하지 않는다.

## 19. 라우팅 알고리즘 비교

### 19.1 Sequence Assignment

전체 customer list의 single route-like global order를 먼저 만들고, workload 기준 contiguous chunk로 나눠 engineer에게 배정한다.

장점:

- 매우 빠름
- 설명이 쉬움
- 균형 잡힌 job block을 만들기 쉬움

약점:

- engineer home awareness가 약함
- 자연스러운 개인 territory를 자를 수 있음
- 강한 skill constraint에 취약함
- final production logic으로는 부적합

### 19.2 Anchor-Based Greedy Assignment

새 job을 engineer의 anchor set과 비교해 가장 적합한 engineer에게 배정한다. Anchor set은 start point와 이미 배정된 customer points다.

장점:

- tail-only growth보다 안정적
- 구현과 유지보수가 단순함
- soft-region과 skill constraint를 적용하기 쉬움

약점:

- 여전히 greedy
- full route insertion cost를 평가하지 않음
- route가 시각적으로 꼬일 수 있음

### 19.3 Iterative Improvement / Local Search

initial assignment를 만든 뒤 one-job move를 반복해 objective를 개선한다.

현재 objective emphasis:

- `max total_work` 감소
- weighted-job imbalance 감소
- travel burden 감소

장점:

- 초기 assignment 운의 영향을 줄임
- 운영 constraint를 유연하게 반영
- LNS로 가는 실용적 중간 단계

약점:

- 전역 최적 보장은 없음
- move operator와 objective 품질에 민감함
- sequence-based 방식보다 느릴 수 있음

### 19.4 OSRM Matrix-Based Iteration

iterative assignment 철학은 유지하되 candidate cost를 OSRM road-network matrix로 계산한다.

장점:

- road-network-aware
- straight-line assignment보다 현실적
- 현재 운영 가능한 heuristic 중 가장 강함

약점:

- line-based mode보다 느림
- full route insertion solver는 아님
- local structure가 나쁘게 고정될 수 있음

권장:

- 현재 live operation 기본값으로 가장 적합하다.

### 19.5 LNS-Style Heuristic

장기 방향:

1. initial feasible solution 생성
2. solution 일부 destroy
3. 제거된 부분 repair/rebuild
4. local improvement 실행
5. time limit 또는 no improvement까지 반복

장점:

- greedy보다 품질 개선 여지가 큼
- operational constraint를 반영하기 좋음
- exact solver보다 운영화가 쉬울 수 있음

약점:

- destroy/repair operator 설계가 중요함
- 최적 보장은 없음

### 19.6 VRP Solver

현재 구현:

- OR-Tools 기반 multi-vehicle VRP
- OSRM matrix 사용
- 3일 비교 slice용

흐름:

1. receipt 기준 job deduplicate
2. engineer start node와 job node 생성
3. start/job 사이 OSRM matrix 생성
4. engineer당 vehicle 생성
5. skill eligibility로 vehicle restriction 적용
6. `480 min` limit을 time dimension에 반영
7. `PATH_CHEAPEST_ARC`, `GUIDED_LOCAL_SEARCH` 사용
8. solved order를 schedule/route output으로 변환

장점:

- true route optimization에 가장 가까움
- assignment와 route order를 함께 풂
- heuristic benchmark로 유용함

약점:

- 유지보수가 복잡함
- custom business penalty를 넣기 까다로움
- 큰 day range에서는 느릴 수 있음
- 아직 live default engine은 아님

## 24. 현재 제약과 주의사항

- 공통모드 alias는 여러 개 정의되어 있지만 실제 mode handler는 일부만 구현되어 있다.

- 공통모드도 여전히 애틀랜타 기준 참조 데이터와 규칙을 일부 공유한다.
- 지역 기준과 capability 규칙은 도시가 늘어나면 별도 seed 전략이 더 필요하다.
- `260310/vrp_api_jobs` 파일 저장 방식은 단순하고 강하지만, 장기적으로는 보관/정리 정책이 필요하다.
- 애틀랜타 생산 라우팅의 DMS2/TV 포함 여부는 문서/모드별 시점에 따라 다르므로 실행 모드의 현재 필터를 반드시 확인해야 한다.
- OSRM 기반 비교는 실제 도로망을 반영하지만 matrix 계산과 final route construction 비용이 크다.
- Common VRP Fill Rate는 배정 slot 수를 technician list capacity로 나눈 값이다. fixed job 보존 때문에 capacity를 넘긴 경우 100% 초과가 정상적으로 표시될 수 있다.
- VRP solver 내부 `max_slots`는 fixed job 처리 중 capacity보다 커질 수 있으므로, 운영 KPI에서는 원래 technician `slot_count`와 구분해서 해석해야 한다.
